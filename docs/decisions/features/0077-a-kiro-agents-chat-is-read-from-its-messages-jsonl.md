# A Kiro agent's chat is read from its messages.jsonl, in the items the app already draws

Decided: 2026-11-13
Status: accepted

Supersedes: features/0063's "an agent on another CLI reads as `supported: false`" and features/0068's "chat ... stay Claude Code's", for Kiro only; Codex still reads as unsupported, and the rest of both stands.
`chat.read` for an agent or Worker that runs on Kiro finds `$KIRO_HOME/sessions/*/<session id>/messages.jsonl` (else `~/.kiro`; the id with or without its `sess_` prefix, the file written last when both exist) and returns the same items, `session`, `start`, `end`, `more` and `state`, paged by byte offset from the tail with `after` and `before`, and across `db::agent_sessions` with the renewal divider, as for Claude. A session with no file yet is `supported: true` with no items. Which CLI an agent runs on is found as at its start (`cli::recovered`), so a Kiro chosen by `settings.json` or a Profile counts, not only one picked for the agent.
`kiro_chat.rs` turns one line (`{id, timestamp, payload:{type, ...}}`) into items; a line that is not JSON, and a last line still being written, are skipped, and only whole lines are read.
- `user`: a `user` item, unless it is empty, starts with `<session_context>`, `<system-reminder>` or `[LIVE STEERING`, or carries `_meta.kiro.syntheticUserMessageReason` or `steeringClearedIds`. A message typed while a turn runs is written three times (the text with `source: steer`, a synthetic copy in a steering notice, an empty clearing entry); only the text shows. `chat::mark_origins` tags Echo's texts, also those Kiro received as `Message: <text>` (features/0072).
- `assistant`: a `reply` when its `operationType` is `Say`; `Reasoning` is not shown.
- `tool_call`: a `tool` item whose id is the `toolCallId`. `execute_bash` and `run_command` are "Bash" (summary: the command's first line, detail: the command), `read_file` is "Read", `fs_write` is "Write" (new: `text`), `str_replace` is "Edit" (old: `old_str`, new: `new_str`), `fs_append` is "Edit" (new: `text`), the file path is the summary; any other tool keeps its `toolName` with its query, pattern, path or first text. An empty summary falls back to `title`. A call with status `denied` carries `denied: true` and gets a `result` "Denied" with `error: true` at once; Kiro's own result follows.
- `tool_result`: a `result` with the same id, `error` when `success` is false, the text cut as for Claude (40 lines, 20,000 characters).
- `turn_end` with `stopReason` `cancelled`: an `event` "Interrupted" with `level: "interrupt"`. `session_metadata` with `key` `displayError`: an `event` "Error: <message>" with `level: "error"`, shown where Kiro wrote it; a `turn_end` with `error` adds "Error: the turn failed." only when no `displayError` came since the turn started.
- Not shown: `turn_start`, `usage_summary`, `session_event`, `session_metadata` `contextUsage`, `session_start`, `agent_note`, `steering_inclusion`, `ContextualHookInvoked`, `pending_interaction`, `interaction_resolved`.
A page of fewer items than asked for starts at byte 0, so "older" does not offer an empty page after the lines Kiro writes before the first message.
`chat.commands` for a Kiro agent returns an empty list: Echo knows no fixed list of Kiro's slash commands, and Claude Code's must not be offered.
Why: Kiro's session file is the one place the daemon can read what happened without scraping the screen, and drawing it as Claude's items needs nothing new in the app; the interrupt and error events and the `denied` flag are additive fields the app may draw later.
Rejected: showing `Reasoning`, which is the model thinking aloud and not part of the conversation; one error event from `turn_end` alone, which would lose the message when the `displayError` line and the end of the turn arrive in two reads.
